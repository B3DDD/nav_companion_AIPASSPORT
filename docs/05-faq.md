# 设计问答

这里记录"为什么这么做"，而不是"怎么用"。用法见 [04-usage.md](04-usage.md)。

## 为什么卡片不自己定位？

卡片没有 GPS 模块，加也加不了（硬件已定）。即使有，卡片屏小、按键少，承担路径规划也不现实。让手机算、卡片看，是这套硬件下最合理的分工，也顺带让固件足够小、启动足够快。

## CP 是怎么识别出来的？

CP 来自 GPX 里的**命名航点**：`<wpt>`（标准写法，两步路/高驰导出都有）或带 `<name>` 的 `<rtept>`（两步路路书常用）。

识别时会排除两类"不是 CP"的点：

1. **名字**含「起终点 / 起点 / 终点 / 出发 / 完赛 / start / finish」；
2. **位置**落在距路线起点或终点 100 米以内——这覆盖了名字没写"起点"的情况（比如叫「停车场」「大门口」）。

为什么必须排除终点：有些赛事的起点和终点不在同一地点，终点同样是个命名航点，如果不排除就会被当成最后一个 CP，导致"距终点"永远算不出来。

## 起点 100 米锚定会不会太严格？

这是个刻意的取舍。不锚定的话，从点「开始导航」那一刻就开始累计——在起点区域热身、拍照、排队的几百米会全部计入成绩，反而更不可信。

100 米 + 连续两次确认，是为了同时解决两件事：

- 避免 GPS 偶尔飘进圈里就误触发；
- 让跑者在起点附近走动时不会被"闪一下就出发"。

如果确实需要在别处测试，可以选一条起点就在身边的路线。

## 反穿是怎么实现的？

内部统一换算成**逻辑索引**：

```
logic 0 ─────────────▶ logic n-1      （始终表示行进方向上的 起点 → 终点）
实际索引 = 正穿 ? logic : n - 1 - logic
```

剩余里程、前方参考点、CP 排序、进度全部基于逻辑索引，方向只在一个映射函数里体现。这样正穿和反穿走的是同一套代码，不会出现"只改了一半"的偏差。

## 累计爬升为什么和手表对不上？

高度数据来源不同：手表多用气压计，手机用 GPS 高度。GPS 高度噪声可达 ±10 米，直接累加会虚高得离谱。

本项目的处理：

1. 高度先做 **3 点滑动平均**；
2. 再以 **3 米滞回**累计正增量（爬够 3 米才算数，回落不超过 3 米不重置基准）。

即便如此，它仍然只是"GPS 高度的合理估计"，不追求与气压计一致。要精确爬升，以手表为准；本项目的爬升用于**感知强度**，不用于成绩核算。

## 距离是怎么算的？

- 水平距离用 Haversine 公式；
- 逐点累加时叠加高度差，但**垂直分量限制在 0.6×水平距离内**（约 31° 坡），避免 GPS 高度噪声把里程吹大；
- 三重过滤：精度 > 30 m 丢弃、速度 > 36 km/h 视为跳点、跳点不累加距离但仍推进参考点。

## 为什么偏离分 30 / 100 两档？

- **30 m**：大多数越野赛道的路宽 + GPS 误差范围，小于这个数值基本可以认为"在线上"；
- **100 m**：明显走岔了，需要回头或切回去。

分两档而不是连续渐变，是因为低头看一眼只需要判断"颜色"，不需要读数字。

## 信号丢失为什么不清空？

越野中信号短暂丢失是常态（林间、谷底、隧道）。清空会让屏幕变成一片 `--`，跑者反而不知道刚才到哪了。

所以卡片**保留最后一次有效读数**，同时把状态和偏离颜色转橙——数字还在，但明确告诉你"这是旧的"。这是"可用性优先于绝对新鲜"的选择。

## 为什么中文字体要自己生成？

LVGL 内置的中文子集（`lv_font_source_han_sans_sc_16_cjk`）只覆盖约 1456 个常用字，"垭口""崴""码头"这类越野地名用字时常缺失，会显示成方块。

所以用 `lv_font_conv` 从黑体生成了覆盖 GB2312 全部 7726 字的点阵字体（4bpp 未压缩，约 6 MB 源码）。代价是固件变大，换来的是任何中文地名都能正常显示。

注意：**不能用压缩格式**，否则需要额外的解码器支持，未启用时会整屏方块。

## 为什么协议用文本而不是二进制？

- 调试时能直接用串口/日志看清每一帧；
- 新增字段时向后兼容更简单（文本字段可空）；
- 帧长最多约 190 字节，2 秒一帧的带宽压力可以忽略。

代价是解析比二进制稍慢、长度校验要自己做（缓冲区 224 字节，超长丢弃）。

## 为什么只有 Android？

因为开发者的主力机是安卓，iOS 的 BLE 后台与定位权限模型完全不同，没有对应设备就无法验证——与其发一个没测过的 iOS 版本，不如先做好一端。

## 数据到底可不可信？

内置了三个自查手段：

1. **「累计 + 剩余 ≈ 路线总长」**——数据页最后两行，两个数加起来和路线总长差得远，说明轨迹匹配或定位出了问题；
2. **「距起点 XXX」**——出发前就能看出定位是否正常（在起点附近应该只有几百米）；
3. **App 的轨迹信息行**——显示识别到的点数、CP 个数、总爬升，和 GPX 对不对得上，一眼可知。

建议的验证方式：同一条 GPX，用手表、两步路、本设备同时跑一遍，对比剩余里程与累计距离的偏差。
